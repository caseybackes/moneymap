# Money Map — Product and UX Backlog

This is a decision and implementation queue. Items are intentionally recorded before a build pass; no item is an authorization to change behavior without its stated decision being made.

## Current UI pass

- [ ] **Responsive dashboard composition grid** — Replace the dashboard's unconstrained two-column stacking with a bounded responsive grid in which each widget declares preferred/minimum spans, compact and expanded variants, and a maximum useful height. Favor dense, low-vertical layouts without allowing arbitrary reordering that makes the page unstable between launches. At desktop width, Accounts & cards should preferentially use wider horizontal space, cap its default preview to a small number of account cards/rows, and offer `Show more` or an account-page drill-in rather than growing indefinitely. Recent transactions, upcoming activity, recurring suggestions, and future widgets fill compatible grid slots instead of leaving large empty panels. Define internal scrolling only where a fixed-height preview remains useful; otherwise use explicit pagination/load-more.
- [ ] **Content-aware launch geometry** — Set a practical desktop default launch size and sensible minimums based on the primary dashboard composition, then preserve a user's explicit window resize/position. The first launch should reveal the core dashboard without horizontal clipping or needless manual resizing at common Windows display sizes; no window size can guarantee that every possible account list fits without scrolling, so widget caps and drill-ins are part of this requirement.
- [ ] **First-run onboarding and local profile** — Add a brief, dismissible first-run sequence after the first-launch dashboard is useful on its own. Establish an optional local display name/profile label for this Windows installation, explain that financial records are encrypted locally, and present clear first actions: connect an account or begin with manual entry. Point to the ledger, calendar, accounts, and settings/profile controls. It must never require a financial connection, cloud account, or app password to use the core local workflow; profile/goals/privacy details remain editable later from the bottom-rail profile menu.
- [ ] **First-party confirmation coverage** — The app-styled confirmation dialog now handles institution disconnect. Replace remaining browser-native confirmations, including transaction deletion, and apply the same treatment to future destructive actions.
- [ ] **Navigation visual direction** — Decide between a refined fixed side rail and top tabs before restructuring navigation. Adopt a coherent free icon set with clear labels/tooltips; candidate implementation source: Lucide (MIT).
- [ ] **Settings and About** — Add a Settings route with persisted user preferences, initially font-size selection and an About/build-information panel. Build information shows product version, build channel (`Dev` or `Production`), build timestamp/commit where available, desktop/runtime versions, and key dependency versions relevant to support.
- [ ] **Bottom-of-rail profile menu** — Place a persistent user-profile icon at the bottom of the fixed navigation rail, visually separated from primary view icons. Clicking it opens an anchored account/options menu, similar in interaction to the desktop ChatGPT profile menu. Initial items: Profile and goals, AI-memory/privacy controls, Settings, Appearance, and About/build information. It remains visible while page content scrolls and light-dismisses when the user clicks elsewhere.
- [ ] **Appearance themes** — Add locally persisted color-theme selection through the profile menu's Appearance entry. Ship a small curated set of accessible themes, including the current dark theme, and apply the choice consistently to application background, widgets, navigation rail, controls, charts, and status states without changing financial data or behavior.
- [ ] **Masked account identifiers** — Show the last four digits for connected checking, savings, and credit accounts wherever account identity matters, using conventional masked display such as `•••• 1234` (or `****1234` where plain text is required). Use the provider-supplied account mask only; do not store full account or card numbers for this feature.
- [ ] **Sensitive-number storage decision** — Before storing any full account, routing, or card number, define whether the product needs it, the encryption/key model, access controls, export/deletion behavior, and recovery semantics. Evaluate OS credential protection versus a user-controlled app passphrase only in the context of an explicit product need; Money Map currently has no app username/password model.

## Environment boundary (decision and implementation design)

- [ ] **Two deployments, two app configurations** — Dev uses a Sandbox-only Worker deployment, Sandbox credentials, development bundle identifier/data directory, and a visible `Development / Sandbox` marker. Production uses a separate Worker deployment, production-only credentials, production bundle identifier/data directory, and has no Sandbox bootstrap/reset route compiled into the app. This is build configuration, not a runtime toggle.
- [ ] **No credential crossover** — A production build rejects Sandbox endpoints and Sandbox Link tokens; a dev build has no production broker URL or production secret path. CI/build validation fails if environments are crossed.
- [ ] **Production connection recovery and backup** — Before the first real Plaid Item is created, add a user-directed encrypted local-backup/restore path and a documented recovery posture for lost local connection metadata. The desktop database currently holds the per-connection broker key while the Worker holds the encrypted Plaid access token; deleting the local database does not delete or refund the upstream Item, but it can leave the user unable to sync or disconnect it from that installation. A Production reset must never silently create a replacement Item. Recovery must either restore the encrypted local state or clearly require a deliberate disconnect/reconnect decision with the Trial-slot consequence shown before action.

## v1.0 architecture foundation

Money Map reaches v1.0 when it has a stable core for a growing, varied financial picture: providers can be added without creating parallel data models or bespoke dashboard logic, and new views can be composed from trusted building blocks. This is an extensibility milestone, not a promise to pre-build every possible financial integration.

- [ ] **Canonical financial domain and provenance** — Establish one encrypted local model for institutions/connections, accounts, balances, transactions, holdings, positions, scheduled activity, and source snapshots. Every imported or manual fact carries source, provider identifier, observed-at time, sync time, and deletion/disconnect ownership so analysis can explain where a number came from.
- [ ] **Connector contract** — Define a provider-module interface for authorization, account selection, sync, normalization, connection status, error/re-auth handling, and destructive disconnect cleanup. Plaid, TradeStation, manual entry/import, and future providers implement this contract; their credentials and refresh tokens remain in the appropriate OS-protected or server-side boundary.
- [ ] **Feature-module boundary** — Split desktop React views into domain-focused modules (Dashboard, Accounts, Ledger, Calendar, Investments, Planning, Settings) with typed query/state interfaces. Views consume canonical data and connector status rather than provider-specific payloads.
- [ ] **Widget and query registry** — Create a controlled catalog of reusable metric, chart, table, timeline, account-card, filter, and explanatory-detail widgets, each bound to typed local queries and clear empty/error/loading states. Dashboard and future pages are composed from this registry instead of duplicated one-off presentation logic.
- [ ] **Agent-composed custom views** — Permit future AI-assisted custom pages to save inspectable view definitions that arrange approved widgets and typed queries. The agent may compose and explain a view, but cannot introduce arbitrary executable UI code, unbounded data access, or hidden financial mutations.
- [ ] **In-context AI copilot and UI referencing** — Add a persistent, dismissible assistant surface docked to the lower-right of the desktop window that can discuss the current financial picture and, with the user's explicit navigation intent, move between existing Money Map views. The copilot can create structured references from specific chat terms to relevant rendered UI targets: hover or click on a referenced term reveals a restrained animated connector/callout to the associated widget, chart point, transaction group, account, or form field; the target receives a clear focus/highlight state and remains keyboard-accessible. Use references selectively for non-obvious evidence or navigation, never as constant visual noise. References must be typed, inspectable, scoped to currently rendered data, and degrade gracefully when a target is absent. The copilot may explain, filter, navigate, draft, or propose; any financial-data mutation, connection action, or external effect still requires explicit confirmation in the native UI.
- [ ] **Extension quality gates** — Require each connector/widget/view to define permissions, data provenance, encrypted-storage behavior, sync and retry semantics, disconnect/deletion behavior, diagnostics, and tests before it becomes part of a production build.

## v1.3 personal dashboard composition

Build on the v1.0 widget/query registry with a user-owned dashboard layout. Each installation has its own saved presentation preferences; this is a display choice, not a separate financial profile or data model.

- [ ] **Editable dashboard layout** — Add an explicit `Customize dashboard` mode in which widgets enter a clear edit state, can be reordered by drag-and-drop or keyboard controls, resized only to supported grid footprints, hidden, restored, and added from an approved widget gallery. Use a stable responsive grid with named sizes (for example compact 2×2, medium 4×2, wide 4×4) rather than freeform pixel positioning. Show a concise preview and description before adding a widget; prevent invalid overlaps and preserve a usable layout at supported window sizes.
- [ ] **Dashboard preferences and recovery** — Persist the layout locally with versioned layout metadata, screen-size fallbacks, and a one-click `Restore default dashboard`. New widgets appear in the gallery first rather than silently rearranging the user's dashboard. Provide accessible keyboard reordering/resizing and retain the same financial-data permissions and provenance whether a widget is default or user-placed.

## Public-beta user lifecycle (before inviting users beyond trusted family)

Money Map can remain local-first while offering an optional account-backed layer for people who want connected accounts, recovery, multi-device use, or a paid service. A device-local profile and a cloud identity are separate concepts: sharing an email address is not required merely to use local budgeting features.

- [ ] **Identity and tenancy decision** — Define two supported modes: local-only profile (no email/login, encrypted records remain on one device) and optional account-backed profile (verified identity, one user-owned cloud tenancy, secure device association, recovery, support, and billing boundary). Do not create a shared household profile by accident; each person owns a separate profile and may choose to share data later through an explicit product feature.
- [ ] **Consumer onboarding lifecycle** — Design an onboarding flow that establishes the local encrypted profile first, makes account connection optional, clearly identifies data held locally versus remote connection metadata, and obtains product-specific consent before Plaid, TradeStation, AI, or other providers are activated. A connected user sees connection status, supported data scopes, sync behavior, and an understandable way to disconnect or delete.
- [ ] **Offboarding and uninstall lifecycle** — Package a standard Windows uninstaller, but never automatically destroy financial records merely because the executable is removed. Offer explicit choices: uninstall application only; erase encrypted device data; disconnect a provider and delete its imported local data; and, for account-backed users, delete the cloud profile and revoke/delete remote provider tokens. Explain permanence, backup options, and provider/Trial-item consequences before confirmation. Complete remote revocation while the app is still authenticated; an uninstaller alone cannot safely infer or recover a deleted local profile's remote connection authority.
- [ ] **Small-public-beta operations** — Before inviting a limited external cohort, establish per-user isolation in Worker/D1 records, rate limits, audit/diagnostic boundaries without financial payload logging, support/recovery procedures, a privacy notice, cost monitoring, and incident/offboarding playbooks. Keep the beta limited and invitation-controlled until its data lifecycle and provider costs are verified.

## Plaid product scope and pricing decision

- [ ] **v0.1 Plaid scope** — Limit the initial Production request to conventional checking, savings, and credit-card synchronization: Link account selection, account/balance display, and posted transaction history/sync. Do not request Investments, Liabilities, Income/Payroll, Auth/routing data, Identity, Assets, Statements, recurring-transactions add-ons, or transactions-refresh add-ons in v0.1 unless a specific accepted pricing proposal and feature decision changes this scope.
- [ ] **v1.0 investment scope** — Add Plaid Investments only after the local investment model and brokerage/retirement experience are ready. Request the exact product pricing, supported account types/institutions, refresh behavior, holdings/transaction coverage, data freshness fields, consent wording, and disconnect semantics separately from conventional banking/credit-card sync.
- [ ] **Plaid sales quote request** — Obtain a written Pay-as-you-go proposal for the precise initial product set and answers to: pricing unit (Item, account, user, or call); monthly charge per active Item; balances/sync/initial historical pull charges; selected-account behavior; duplicate/reconnect/re-auth billing; Trial-to-paid transition; deletion timing and billing stop; minimums, commitment, support, and overages. Price every proposed v1 product independently before enabling it.
- [ ] **Plaid cost-aware sync policy** — Use the cached account balances returned by Transaction Sync or free `/accounts/get` for ordinary startup synchronization and display their freshness timestamp. Reserve paid real-time Balance extraction for an explicitly requested, clearly labeled need; never invoke it automatically on app launch or a recurring default cadence. Keep timestamped local snapshots, enforce per-user/per-connection rate limits for paid calls in the broker, and record request counts and estimated cost without logging financial payloads. Expose a connection-cost diagnostic before public beta.

## Analytics as the primary product value

Data connection and manual entry are ingestion paths. The product's central value is a trustworthy analysis layer over the user's complete financial picture.

- [ ] **Explainable forward net-worth forecast** — Extend the Dashboard Net worth widget into one continuous actual-and-forecast chart. The user selects a forward horizon from 1 month through 5 years; the chart retains historical actual balances through today, then projects the local financial picture forward. Keep the existing period controls and show selected-period income, spending, and net flow in the same widget.
- [ ] **Forecast inputs and calibration** — Project known cash flows deterministically from selected connected accounts, manual balances, scheduled transactions, and user-confirmed future events. Add a transparent time-series baseline for recurring or seasonal cash flow that is not explicitly scheduled, with separate confidence/freshness indicators. Users must be able to confirm, edit, exclude, or override every inferred forecast input.
- [ ] **Material-event annotations** — Mark material forecast rises and drops directly on the chart. A compact `?` affordance on each marker opens an explanation showing the contributing transactions/events, amounts, dates, whether each input is observed, scheduled, or estimated, and its effect on projected net worth.
- [ ] **Tax-aware event modeling** — Support user-entered or explicitly confirmed tax obligations, withholding, refunds, and payment dates as forecast events. Do not infer a tax liability solely from bank transactions; show tax estimates and assumptions separately from confirmed tax payments.
- [ ] **Payroll-income data discovery** — Evaluate whether Plaid Income / Payroll Income can responsibly add pay, withholding, and employer-payroll facts to a local Money Map profile. Confirm current product access, ADP coverage, permitted personal-finance use, cost, consent wording, local encryption/retention, and manual fallback before any integration. The existing Transactions connection does not provide this payroll data.
- [ ] Cluster merchant/payee variants and show explainable category proposals that learn from explicit user corrections.
- [ ] Show category spending, income, cash flow, and trends over selectable time ranges with drill-down to the underlying transactions.
- [ ] Detect recurring payments, unusual changes, and emerging spend patterns with evidence and user approval before any record changes.
- [ ] Keep what-if modeling numerical and structured; provide AI interpretation only after the scenario calculation is complete.
- [ ] Later: offer evidence-backed financial opportunity analysis across user-provided account, insurance, and tax information: possible savings, coverage gaps, and tax-impact questions. Present assumptions, confidence, and caveats; require user review and never perform an action automatically.
- [ ] Define the privacy/consent model before any external AI receives financial data. Preserve local-first operation when no provider is configured.

## AI financial-planning harness (discovery before implementation)

The goal is a user-controlled planning partner that connects the user's full financial picture: banking, credit, insurance, investments, taxes, credit health, and stated goals. It produces evidence-linked observations, questions, options, and numerical plans; it does not initiate financial, insurance, tax, or investment actions.

- [ ] **Financial profile and goals** — Model the user's household-independent objectives, constraints, time horizon, risk preferences, life events, and explicit corrections. Each app installation remains one independent profile; a family member uses their own installation/profile.
- [ ] **Structured financial facts** — Keep canonical balances, transactions, holdings, coverage, tax inputs, and source dates in the encrypted local database. AI summaries and memories must link back to source records, carry confidence/freshness, and never become the authoritative financial record.
- [ ] **Action-item engine** — Surface prioritised opportunities and questions across categories such as cash flow, debt, insurance coverage, tax planning, and investments. Every item must show its inputs, assumptions, numerical effect where calculable, and a user-approved status; retain a decision history.
- [ ] **Cross-domain planning workspace** — Add dedicated domain views and structured inputs for insurance, investments/retirement, taxes, credit/debt, and benefits as the relevant data model matures. Their purpose is to complete the user's financial picture and support cross-domain planning, not to create disconnected dashboards.
- [ ] **Decision-ready planning brief** — Turn the highest-value observations into a concise plan: material issue/opportunity, evidence, cross-domain linkage, assumptions, numerical scenarios, unanswered questions, next action, and recommended professional review where appropriate.
- [ ] **AI conversation and memory** — Make long-lived conversational memory optional and inspectable. Separate explicit user preferences/goals, verified financial facts, derived summaries, and conversation history; allow view, correction, export, and deletion for each class.
- [ ] **Local-only memory baseline** — Store structured memory, summaries, source links, retrieval indexes, and any embeddings inside the encrypted local database. Treat embeddings as sensitive derived financial data. Any index must be rebuildable from encrypted canonical records; no memory service, vector store, or Cloudflare storage is required.
- [ ] **Local-only privacy mode** — Define a strict mode in which financial records, memory, retrieval, embeddings, and AI inference remain on-device with no outbound requests. A mode that uses cloud inference while retaining memory locally must disclose that retrieved context is still sent to the selected provider.
- [ ] **Provider-agnostic AI contract** — Define model, embedding, tool-calling, and streaming interfaces independent of a specific provider. Support local inference and user-supplied providers before considering a managed service.
- [ ] **AI tool boundary** — Expose narrowly typed, permission-scoped tools such as read financial summary, retrieve cited transactions, run a numerical scenario, and draft an action item. Tool calls must be auditable and no tool may mutate financial data or trigger an external action without explicit user confirmation.
- [ ] **Cloud AI tier decision** — If a managed tier is offered, use a dedicated broker boundary for authentication, provider credentials, rate limits, billing/metering, and request audit metadata. Define data minimization, per-request consent, retention, encryption/key ownership, deletion, and provider terms before sending financial context off-device.
- [ ] **Memory framework evaluation** — Evaluate Hindsight, Holographic Memory, and similar systems only against the above portability, encryption, deletion, provenance, and provider-agnostic requirements. Do not make a framework the canonical store or provider lock-in point.
- [ ] **MCP and skills boundary** — Application runtime capabilities use typed app tools. MCP is a later optional integration surface for external agents; coding-agent skills are development tooling and are not the Money Map end-user AI runtime.
- [ ] **Advice safety and review** — Present planning output as decision support with uncertainty and source citations. For tax, insurance, investment, or legal decisions, prompt the user to review with the appropriate qualified professional where warranted.
